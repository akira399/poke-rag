## 3. 过程中的工程记录

1. **首轮拉取在列表请求处崩溃**：`list_all`（获取资源清单的 1 个请求）没有重试逻辑，网络抖动（TLS 握手 EOF）直接终止任务。修复：列表请求补退避重试 + 单资源失败不阻断全局（已记录失败、重跑续传）。
   - 教学点：数据管道的每个环节都要问"挂了会怎样"——**列表请求挂 = 全资源挂，因此它比单条目下载更需要兜底**。
2. **断点续传验证**：首轮已下载 3,983 个文件，重跑时只补缺口（skipped 3,983 / ok 536+5），25 分钟的活实际 7 分钟补完——断点续传的价值实测生效。
3. **进化链 5 条首次失败**，重跑即补全（失败的 5 条恰好是被抖掉的那批）。现象说明"重试+续传"组合是把不稳定的第三方拉数据做到可交付的正确姿势。

## 4. 复现命令（数据即代码资产）

```bash
cd poke-rag
.venv/Scripts/python.exe scripts/fetch_pokeapi.py     # PokeAPI 全量（约 25 分钟，断点续传）
node scripts/fetch_showdown.mjs                        # Showdown 规则数据（约 1 分钟）

```

- 三个脚本均为**幂等**：重复执行只补缺口，不重复请求、不破坏已有数据。
- 单测 5/5 通过（纯函数部分不依赖网络）。
